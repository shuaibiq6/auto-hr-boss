# 限频策略

**一句话**：单次强度必须固定在「永远够不到平台阈值」的水平。等待时间不是性能问题，是安全成本。

实现载体：`scripts/pacing.mjs`。所有批量触达的驱动脚本都应向它询问「下一次该等多久」，
不要各自 `sleep(random(...))`——散落的规则无法审计，也无法保证红线优先。

---

## 1. 为什么不能压缩间隔

把一次真实的 20 人触达拆开看：

| 组成 | 耗时 | 占比 |
|---|---|---|
| 页面动作（hover + 点击 + 校验） | 约 33 秒 | **7.4%** |
| 刻意等待（GAP） | 约 413 秒 | **92.6%** |

> 耗时的九成是"故意等出来的"。压缩 GAP 换来的提速，代价是把统计特征从"人"变成"机器"。

想真正缩短总时长，只有两条合规路径：

1. **把 N 人拆成多次会话**（不同时段各跑一批）
2. **降低 N**

两条路都会让"单次强度"下降。而压缩 GAP 会让单次强度上升——方向相反。

---

## 2. 安全档

| 档位 | 定位 | GAP 区间 | 单会话上限 | 日上限 | 活跃时段 |
|---|---|---|---|---|---|
| `conservative` | 红线优先。企业账号 / 首次使用 / 平台近期有动作 | 120–300s | 10 人 | 20 次 | 09:30–11:30 / 14:00–17:30 |
| `balanced` | 风险与体验平衡。经过实测验证 | 75–210s | 25 人 | 45 次 | 09:30–11:30 / 14:00–17:30 |
| `efficient` | 体验优先。任务时间敏感时用 | 60–150s | 30 人 | 60 次 | 09:00–12:00 / 13:30–18:00 |
| **`hr150` ★本版默认** | **招聘端「单日 150 触达」专用。窗口对齐 + 6 会话拆解** | **115–185s** | **30 人** | **150 次** | **09:00–11:50 / 13:30–18:00** |

> **本副本（`boss-hr-outreach-safe`）默认档是 `hr150`，不是 `balanced`。**
> 这是面向 BOSS 招聘端「单日触达量」指标的专用档，参数由**时间窗口反推**得到，
> 完整推导与排班见 [`hr-daily-150-plan.md`](hr-daily-150-plan.md)。

选档建议：

- **不确定就先跑 `conservative`**，观察一到两天无异常再升档。
- 企业账号被处置的代价远高于个人号（影响企业认证与全部在招职位），企业场景建议长期停在 `conservative` 或 `balanced`。
- 同一天内不要跨档混跑（会形成"忽快忽慢"的异常形态）。

### 2.1 窗口反推：日量上限不是配额给的，是窗口给的

这是本版最重要的一条。**「能发多少」和「配额允许多少」是两件事**：

```
净可用秒数 = 窗口总时长 − 窗口前自检 − 会话间隙
单次占用   = GAP 均值 + 页面动作耗时（约 7s）
日量上限   = 净可用秒数 ÷ 单次占用
```

以本版固定窗口 09:00–11:50 + 13:30–18:00 为例：

| 项 | 值 |
|---|---|
| 窗口总时长 | 170 + 270 = **440 分钟 = 26,400 秒** |
| 减：2 次窗口前自检（5 min × 2） | −600 s |
| 减：5 个会话间隙（5 min × 5） | −1,500 s |
| **净可用** | **24,300 s（405 分钟）** |

反推结果：

| GAP 均值 | 单次占用 | 日量上限 | 备注 |
|---|---|---|---|
| 115 s | 122 s | **≈ 200** | 刚好塞满，已逼近机器节奏 |
| 130 s | 137 s | 177 | |
| **145 s** | **152 s** | **160** | **本档取值：见下** |
| 180 s | 187 s | 130 | |
| 210 s | 217 s | 112 | |

**读法**：想让日量到 200，GAP 均值必须压到约 115s；而 145s 是"仍远离 60s 机器下限"的安全值，窗口只能装下 160 次。

**所以本档把日目标定在 150（不是 160）** —— 160 是物理上限，顶着上限跑没有任何容错；150 留出约 10 次的缓冲，用于吸收风险信号导致的间隔拉长（×1.5 → 172–278s）、以及某个会话被拖长的情况。

**这条结论的含义**：`hr150` 里「150」这个数字**不是风控算出来的，是窗口算出来的**。它同时是「安全性 + 效率」双约束下的真实最大值。想突破它，只能改窗口或改 GAP，两者都不建议。

### 2.2 `hr150` 的会话排班（6 会话）

单会话 ≤30 人（硬边界），按下面拆解：

| 会话 | 时间 | 人数 | 说明 |
|---|---|---|---|
| S1 | 09:00–10:16 | 30 | 上午主段 |
| S2 | 10:21–11:37 | 30 | 上午收尾（距 11:50 留 13 min 余量） |
| — | 11:50–13:30 | 0 | **午休停顿（不要跳过）** |
| S3 | 13:30–14:46 | 30 | 下午主段 |
| S4 | 14:51–16:07 | 30 | |
| S5 | 16:12–17:03 | 20 | 递减，开始留缓冲 |
| S6 | 17:08–17:33 | 10 | **收尾缓冲位** |
| | | **150** | |

三个设计要点：

1. **会话之间的 5 分钟间隙本身就是防御。** 它天然形成「操作簇 + 停顿」的交替形态——不需要改 `pacing.mjs` 的抖动模型（均匀 ±15%）就得到了近似长尾的效果。
2. **下午比上午多**（90 vs 60）。下午窗口长 100 分钟，多做合理；真人 HR 下午产出高也更自然。
3. **S6 只排 10 人**是**缓冲位**：若前面某会话触发风险信号被拉长，直接砍掉 S6 即可，不影响主体目标（此时日量 140，仍在安全区）。


## 3. 硬边界（任何档位都不可越过）

| 边界 | 值 | 理由 |
|---|---|---|
| GAP 绝对下限 | **60s** | 低于此值即进入机器节奏，任何档位都不得越过 |
| GAP 绝对上限 | **300s** | 再慢会让会话时长不可预测，且已超出真人浏览行为带；120–300s 覆盖真人区间 |
| 单会话人数 | **30 人** | 单次连续操作的上限 |
| 风险放大系数 | **×1.5** | 命中风险信号时该次间隔的放大倍数（放大后仍受 300s 硬上限约束） |
| 连败熔断 | **连续 2 次** | 连续 2 次触达未确认送达即停止当天剩余操作 |

## 4. 风险信号 → 自动拉长

命中下列任一信号时，**该次** GAP 乘以 1.5（上限 300s），且不中断整批：

| 信号 | 来源 |
|---|---|
| 上一次触达需要重试，或定位失败后补发 | `greet-batch.mjs` 的失败计数 |
| 出现过「页面不可见」（`visibilityState !== visible`） | `risk-check.mjs` 退出码非 0，或 `/restore-window` 被调用 |
| 回执弹窗迟迟不出现，或走了冗余信号才判定成功 | 校验命中「计数下降」而非「文案变化」 |
| 点击曾因遮挡被拒（`/clickSafe` 返回 409） | `/clickSafe` 返回体 `blocked: true` |

命中下列信号时**立即终止当天全部操作**（不是拉长）：

- 验证码 / 滑块
- **被要求答题**（优先级高于验证码——答题是平台已判定违规后的处置动作）
- 出现「操作频繁 / 次数已用完 / 已达上限」
- 登录失效
- 收到明确的拒绝或拉黑

## 5. 命令用法

```bash
# 查看所有档位与硬边界
node scripts/pacing.mjs profiles

# 生成一批的执行时间表（人可读；加 --json 输出机器可读）
# 本版默认档已是 hr150，--profile 可省略
node scripts/pacing.mjs plan --count 30 --profile hr150 --start 09:00

# 让闸门配置与节拍器同源（推荐：参数只维护一处）
node scripts/pacing.mjs plan --count 30 --job screen.job.json

# 取下一次等待秒数（驱动脚本在循环里调用）
node scripts/pacing.mjs next --profile hr150 [--risk] [--last 128] --json
#   --risk  上一次命中风险信号 → 自动 ×1.5
#   --last  上一次实际等待秒数（仅用于日志对比）

# 日额度 / 时段闸门
node scripts/pacing.mjs check --today 90 --profile hr150
#   退出码 0=允许  3=不允许
```

作为库使用：

```js
import { nextGap, resolveProfile, gate, PROFILES, HARD_LIMITS } from './pacing.mjs';

const profile = resolveProfile('balanced');
const gap = nextGap(profile, { index: 3, risk: lastRisk });   // → { seconds, base, reason, risk, atCeil }
await sleep(gap.seconds * 1000);
```

## 6. 与准入闸门的关系

`screen-talent.mjs`（招聘方）与 `preflight.mjs`（求职方）负责**选谁**（G0 红线 / G1 匹配度 / G2 批次 / G3 时序），
`pacing.mjs` 负责**什么时候发**。

两者的 GAP 参数应当**同源**：给 `pacing` 传 `--job <闸门配置>` 即可自动读取
`limits.minGapSeconds / maxGapSeconds / dailyMax / activeWindows`。
只维护闸门配置一处，避免"计划说的"与"实际做的"不一致。

## 7. 想扩大范围怎么办

**不要动 GAP。** 按下面的顺序考虑：

1. **提高匹配度**（最有效）。招聘端的真实风险是「无效触达」——平台量化招聘方的回复率，大量无人回应的招呼会压低职位曝光。
   提高筛选门槛、把精力放在「候选人回复后的第一条消息」，比多发 20 条更有价值。
2. **拆分时段**。同样 45 次，集中在 1 小时发完 vs 分散到上午/下午两个时段，后者单次强度更低。
3. **多日累积**。触达记录跨日累积（`--commit` 回写），冷却期机制会让重复触达被自动拦截。
4. **换更宽松的账号策略**：企业账号风险高于个人账号，若业务允许，用个人账号做低价值触达。

只有在上面都做足、且连续多日无任何风险信号的前提下，才考虑升档（`balanced` → `efficient`），
单次也只升一档。

> **⚠️ 本版补充：固定窗口场景下，"提量"这条路已经被物理封死。**
> 本副本的窗口是固定的（09:00–11:50 / 13:30–18:00），净可用 24,300 秒。
> 在安全 GAP（均值 145s）下，窗口最多装 160 次 —— **这是天花板，与配额无关**。
> 想超过它只有两条路，两条都不建议：
> - **压 GAP**（→115s）换 200 次：把统计特征推向机器节奏，风险自担；
> - **改窗口**（用上更多时段）：等价于恢复"长时间连续操作"，会把单日时长拉到 8–11 小时。
>
> **正解是提高匹配度，不是提高条数**（见第 1 条）。日 150 的三个非 GAP 风险
> （回复率崩塌→职位降权、时间跨度、候选池不足）见 [`hr-daily-150-plan.md`](hr-daily-150-plan.md)。

## 8. 参数自定义

编辑 `templates/actions/*.json` 对应站点的配置，或在调用时传 `--job` 覆盖。
若需要新增档位，在 `pacing.mjs` 的 `PROFILES` 里加一项——但**不要修改 `HARD_LIMITS`**，
那是所有档位共享的红线。
