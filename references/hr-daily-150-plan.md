# 招聘端「单日 150 触达」执行方案

> **一句话**：日 150 这个数字**不是风控给的，也不是配额给的，是时间窗口算出来的**。
> 在安全 GAP（均值 145s）下，固定窗口最多装 160 次 —— 150 是「安全性 + 效率」双约束下的真实最大值。

本文件是 `pacing.mjs` 里 `hr150` 档位的推导依据。参数改动**必须同步改这两处**，否则「计划说的」和「实际做的」会不一致。

---

## 1. 前提（这三条决定了后面所有结论）

| 前提 | 值 | 影响 |
|---|---|---|
| 日触达目标 | **150**（原目标 200，可接受缩水，但要缩水后的最大值） | 决定了 GAP 取值 |
| 可执行窗口（固定） | **09:00–11:50 / 13:30–18:00** | 决定日量天花板 |
| 回复由人工完成 | 是，工具只负责打招呼 | 只降低**投诉**风险，不降低**降权**风险（见 §7.1） |

---

## 2. 时间预算 → GAP 反推

```
净可用秒数 = 窗口总时长 − 窗口前自检 − 会话间隙
单次占用   = GAP 均值 + 页面动作耗时（实测约 7s）
日量上限   = 净可用秒数 ÷ 单次占用
```

### 2.1 净可用时间

| 项 | 值 |
|---|---|
| 上午 09:00–11:50 | 170 分钟 |
| 下午 13:30–18:00 | 270 分钟 |
| 合计 | 440 分钟 = 26,400 秒 |
| 减：窗口前自检（5 min × 2，含 `risk-check.mjs` + 读配额） | −600 s |
| 减：会话间隙（5 min × 5） | −1,500 s |
| **净可用** | **24,300 秒（405 分钟）** |

### 2.2 反推表

| GAP 均值 | 单次占用 | 日量上限 | 评价 |
|---|---|---|---|
| 115 s | 122 s | ≈ **200** | 刚好塞满。比 `balanced` 推荐中值低 30s，已滑向机器节奏 |
| 130 s | 137 s | 177 | 偏紧 |
| **145 s** | **152 s** | **160** | **本档取值。仍远离 60s 机器硬下限** |
| 180 s | 187 s | 130 | 偏保守 |
| 210 s | 217 s | 112 | 过保守 |

**结论：日目标取 150，不取 160。** 160 是物理上限，顶着上限跑没有容错；150 留约 10 次的缓冲，用于吸收风险信号导致的间隔拉长。

---

## 3. 会话排班（6 会话）

单会话 ≤ 30 人（硬边界）。按 30/30/30/30/20/10 拆：

| 会话 | 时间 | 人数 | 说明 |
|---|---|---|---|
| S1 | 09:00–10:16 | 30 | 上午主段 |
| S2 | 10:21–11:37 | 30 | 距 11:50 留 13 min 余量 |
| — | 11:50–13:30 | 0 | **午休停顿，不要跳过** |
| S3 | 13:30–14:46 | 30 | 下午主段 |
| S4 | 14:51–16:07 | 30 | |
| S5 | 16:12–17:03 | 20 | 开始递减 |
| S6 | 17:08–17:33 | 10 | **收尾缓冲位** |
| | | **合计 150** | |

**三个设计要点：**

1. **会话之间的 5 分钟间隙本身就是防御。** 它天然形成「操作簇 + 停顿」的交替形态——比把均匀抖动改成簇状分布更容易实现，效果近似。
2. **下午比上午多**（90 vs 60）。下午窗口长 100 分钟，多做合理；真人 HR 下午产出高也更自然。
3. **S6 只排 10 人是缓冲位。** 若前面某会话触发风险信号被拉长，**直接砍掉 S6**（此时日量 140，仍在安全区），不要压缩前面的间隔去补。

### 3.1 生成计划

```bash
# 上午第一个会话
node scripts/pacing.mjs plan --count 30 --profile hr150 --start 09:00

# 下午第一个会话
node scripts/pacing.mjs plan --count 30 --profile hr150 --start 13:30
```

## 4. GAP 参数

| 参数 | 值 | 说明 |
|---|---|---|
| 区间 | **115–185 s** | 下界从 `balanced` 的 75s 提到 115s —— 75s 会和 60s 硬下限挤在一起，方差波动中容易摸到机器节奏 |
| 均值 | **145 s** | 落在真人 120–300s 区间中部 |
| 抖动 | ±15%（内置） | `pacing.mjs` 的 `JITTER_RATIO`，不需改 |
| 风险拉长 | **×1.5 → 172–278 s** | 仍受 300s 硬上限约束 |
| 硬边界 | 60s / 300s / 单会话 30 人 | **任何档位都不可越过** |

## 5. 风控检查点（跟排班配套）

| 时点 | 动作 |
|---|---|
| 09:00 / 13:30 | 读 App 内「今日剩余主动开聊次数」；跑 `risk-check.mjs` |
| 每个会话开始前 | `pacing.mjs check --today <已发数> --profile hr150`，确认额度与时段 |
| 每个会话结束后 | **查配额消耗是否等于实际发送数** —— 对不上就是信号；记录任何异常弹窗 |
| 会话中 | 验证码 / 答题 → **立即停止全天**；连败 2 次未确认送达 → 停止当天剩余 |
| 全天 | **目标 150 达到即收，不要为了凑数硬跑** |

### 5.1 分级熔断（不是单次拉长）

出现风险信号时的处理**不是只把间隔 ×1.5**，而是按级降级当日目标：

| 级别 | 触发 | 处置 |
|---|---|---|
| 轻度 | 单次未确认送达 / 页面不可见并已恢复 | 该次间隔 ×1.5；当日目标不变 |
| 中度 | 连续 2 次未确认送达、或配额消耗对不上 | 停止当前会话；**当日目标降 30**（150 → 120） |
| 重度 | 验证码 / 答题 / 「操作频繁」/ 登录失效 | **立即停止当天全部操作**，次日不恢复原量 |

---

## 6. 前置爬坡（对冲「基线突变」）

**账号历史 50 次/天，直接拉到 150，是 3 倍突跳。** 风控看的是相对**你自己历史基线**的偏离，不是绝对值。爬坡能把这个特征消解掉：

| 天 | 日量 |
|---|---|
| D1–D3 | 50–60 |
| D4–D5 | 80–100 |
| D6–D7 | 120–150 |
| 自 D8 起 | 150（`hr150` 目标值） |

爬到第 8 天，账号历史基线已被抬到 120–150 —— 150 相对基线只是 **1.0–1.25×**，突变特征基本消失。

> **只在"每天都要跑"时才值得爬坡。** 如果 150 是一次性指标，爬坡来不及，那就把重心全押在 §5 熔断 和 §7.1 匹配度上。

---

## 7. 三条与 GAP 无关的风险（别忽略）

### 7.1 回复率崩塌 → 职位降权（自动生效，不需要"被抓"）

招聘端的首要风险不是被投诉，而是**无效触达**。平台量化招聘方的回复率：

- 50 发出、回 10–15 个 = 20–30%，像正常 HR
- **150 发出、只回 10 个 = 6.7%** → 判定**低质量触达** → **压低职位曝光**

**这条与"有没有被拦住"完全无关，机器自动执行。** 而且人工回复救不了它：人工能改的是「已经回你的人聊得好不好」（影响投诉率与转化率），改不了「发出去的 150 条里有多少人愿意理你」（那个分子由候选人兴趣决定）。

> **闭环陷阱**：想凑满 150 → 必须放宽筛选闸门 → 回复率进一步下降 → 更坐实低质量触达。
> **宁可少发，不要为凑数降标准。**

### 7.2 候选池可能比时间更硬

按实测 8% 闸门通过率，150 人需要筛约 **1,875 张卡**。推荐流不是无限池（实测跨一次重载仅约 10% 重合）。
**开工第一天先实测"窗口内最多能滚出多少合格候选人"，用这个数反过来定当日目标。** 只能筛出 100 个，那 150 就是空指标。

### 7.3 转化闭环（有平台侧的负面特征记录）

平台把「大量邀约无面试、面试无评价」列为**低活跃**特征 → 减少岗位流量推荐。日 150 必须配：

- 人工及时回复（已有）
- 把回复者推进到面试，不要聊两句就断
- **面试后在平台上完成评价**（最常被漏掉的一步）
- 定期维护/刷新职位（岗位长期不改也是负面特征）

## 8. 硬纪律

1. **不要在脚本运行时用同一账号在手机端并发操作。** 两设备并行会破坏 `pacing.mjs` 的 GAP 方差设计（两条流间隔交错，账号级操作密度反而升高），并新增「多设备并发」这一独立风控因子。
2. **手机端的每一次触达，当天必须补录进台账。** `--commit` 只记脚本自己发的；不补录则 30 天冷却期（`repeatTalentCooldownDays`）形同虚设，**重复触达是明确的风控项**。
3. **不要从 50 直接跳 150。** 见 §6。
4. **观测指标是回复率，不是"有没有警告"。** 风控扣分你看不见，回复率你看得见 —— 跌破 15% 立即降档，这是硬闸。
5. **「这次没被拦截」不构成下次加码的依据。** 平台的处置是**累积评分 + 阈值触发**，没被拦是运气不是许可。

## 9. 开工前必须先实测的四件事

| # | 实测项 | 决定什么 |
|---|---|---|
| 1 | App 内「今日剩余主动开聊次数」实际是多少 | `dailyMax` 能否取到 150；免费/基础档可能只有 3–10 |
| 2 | 窗口内最多能滚出多少**合格**候选人 | 150 是空指标还是能落地（见 §7.2） |
| 3 | 同一账号「配额升级后立刻拉满」是否触发信号 | 决定爬坡是否必须（见 §6） |
| 4 | 「已查看」/「职位邀请」两条**不占配额**通道在 web 端是否可用 | 可用则不必把 150 全压在主动开聊上，风险结构更优 |
